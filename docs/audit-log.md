# Audit Logging

## Purpose

The audit log provides an immutable, chronological record of all sensitive actions performed within an organization. It is used for:

- Security investigations ("who accessed this patient's record?")
- Compliance auditing (HIPAA requires tracking access to protected health information)
- Operational troubleshooting ("who cancelled this appointment and when?")

---

## Append-Only Design

The `AuditLog` table has no `UPDATE` or `DELETE` operations anywhere in the codebase. Every record is written once and never modified. The only query operations on `AuditLog` are `create` and `findMany`.

The primary key is a CUID generated by the database. There are no soft-delete flags, no `updatedAt` column, and no mechanism to hide records.

---

## What Is Logged

Every sensitive action is captured:

| Action | Trigger |
|---|---|
| `user.login` | Successful login |
| `user.logout` | Logout |
| `user.invited` | Staff invitation sent |
| `user.role_changed` | Membership role updated |
| `patient.created` | New patient registered |
| `patient.viewed` | Patient detail page or API fetch |
| `patient.updated` | Demographics or contact info changed |
| `patient.deleted` | Patient deactivated |
| `clinical_note.viewed` | Clinical note fetched via API |
| `clinical_note.created` | New draft created |
| `clinical_note.updated` | Draft content saved |
| `clinical_note.finalized` | Note signed off |
| `clinical_note.amended` | Note amended after finalization |
| `appointment.created` | New appointment booked |
| `appointment.modified` | Appointment time or details changed |
| `appointment.cancelled` | Appointment cancelled |
| `appointment.checked_in` | Patient checked in |
| `encounter.created` | New encounter opened |
| `document.accessed` | Document URL fetched |
| `document.uploaded` | File uploaded |
| `document.deleted` | Document deleted |
| `organization.created` | New org registered |
| `organization.updated` | Org settings changed |

## What Is Never Logged

The following are intentionally excluded from all audit log entries and metadata:

- Clinical note content (chief complaint, observations, assessment, plan)
- Patient names, dates of birth, or other demographics
- Passwords or password hashes
- Session tokens
- Insurance policy numbers or payment information

Audit log records contain only non-sensitive identifiers and metadata:

```typescript
interface AuditParams {
  organizationId: string;   // Which org
  actorUserId?: string;     // Who did it (null for system actions)
  action: AuditAction;      // What was done
  resourceType: string;     // Which entity type ("Patient", "ClinicalNote", etc.)
  resourceId: string;       // Which specific record
  requestId?: string;       // Correlation ID for distributed tracing
  ipAddress?: string;       // Caller's IP (first non-proxy from X-Forwarded-For)
  metadata?: Record<string, unknown>; // Non-sensitive context (e.g., amendment version number)
}
```

## Non-Crashing Guarantee

The `createAuditLog()` function wraps its database write in a try/catch:

```typescript
export async function createAuditLog(params: AuditParams): Promise<void> {
  await db.auditLog
    .create({ data: { ... } })
    .catch((err) => {
      console.error("[audit] Failed to write audit log:", err);
    });
}
```

If the audit write fails (database unavailable, connection timeout, disk full), the error is logged to stderr and swallowed. The main request completes normally.

This is a deliberate trade-off: losing an audit record is less harmful than rejecting a valid clinical action. In a production system, a secondary audit sink (structured logging to a log aggregator like Datadog or CloudWatch) would serve as a backup.

---

## Request Correlation

Every `ApiContext` includes a `requestId` generated at the start of the request:

```typescript
const requestId = uuidv4();
```

This ID flows into every audit log entry created during that request. If multiple entities are modified in a single request (e.g., creating a patient and their contact info), all resulting audit logs share the same `requestId`, making it easy to reconstruct what a single API call did.

---

## Viewing the Audit Log

OWNER and ADMIN roles can view the audit log at `/org/[orgSlug]/audit`. The page displays:

- Action name
- Actor (user who performed the action)
- Resource type and ID
- Timestamp
- IP address

The `GET /api/audit` endpoint supports filtering by `resourceType`, `resourceId`, `actorUserId`, and date range.

---

## Storage Considerations

The audit log is high-write and never updated. For production:

- Add a partial index on `(organizationId, createdAt DESC)` for the dashboard query
- Consider partitioning the `AuditLog` table by month for orgs with high activity
- Archive records older than a retention window (e.g., 7 years for HIPAA compliance) to cold storage rather than deleting them
